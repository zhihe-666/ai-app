# PRD智能生成系统方案

---

## 一、项目背景与目标

### 1\.1 项目背景

当前团队在内部平台新功能开发中可能会遇到以下问题：

- **需求表达零散**：算法工程师和数据科学家的需求常以口头沟通、会议纪要或碎片化文字传递，缺乏结构化沉淀。

- **PRD撰写耗时**：从零散信息到规范化PRD的转化依赖人工整理，效率低且易遗漏边界场景（如训练任务并发上限、模型版本回滚等）。

- **上下文割裂**：新功能开发常需回溯历史PRD及平台架构，信息检索成本高。

- **设计与开发脱节**：PRD描述的功能需人工转化为UI原型，前后端沟通成本高。

### 1\.2 项目目标

构建一套**AI原生**的PRD生成工作台，服务于在线机器学习平台的新功能研发，实现：

1. **多模式生成**：支持简单、中等、深度三种模式，适配从轻量需求到复杂功能的不同复杂度。

2. **知识驱动**：沉淀历史PRD与平台文档，形成可检索、可复用的企业知识库，并演进至GraphRAG建立全局业务拓扑认知。

3. **上下文感知**：基于平台架构快照与知识图谱，确保生成内容贴合实际技术生态，自动识别跨模块影响。

4. **双轨交付**：输出人类可读的Markdown PRD \+ 机器可读的结构化Spec，打通"AI写PRD"到"AI写代码"的闭环。

5. **高保真原型**：通过JSON Schema驱动的动态渲染引擎，生成100%符合平台UI规范的前端原型。

## 二、系统整体架构

系统采用分层架构设计，包含**输入层**、**知识层**、**模型层**、**处理层**、**输出层**与**交互层**六大层级。

**核心设计原则**：

- 输入层各来源（文字需求、飞书妙记链接、历史PRD文件）为**并行可选**关系，用户可灵活选用任一或多种组合。

- 输入素材按时效性自动分流为"临时上下文"与"长期知识"，避免知识库污染。

- 知识层独立服务于所有生成模式，从向量检索逐步演进至GraphRAG图谱推理。

- 模型层采用"推理\+协同"双模型架构，按任务复杂度动态调度。

- 处理层基于LangGraph编排引擎，支持复杂状态流转与逆向跳转。

- 输出层实现双轨交付：人类可读Markdown \+ 机器可读Spec Schema。

**各层职责说明**：

|层级|职责|关键特性|
|---|---|---|
|**输入层**|接收用户提交的原始素材，按时效性自动分流|文字描述、飞书妙记链接、文件导入三者**并行可选**；文件自动分类为"临时上下文"与"长期知识"|
|**知识层**|存储并检索平台级上下文|向量检索 \+ GraphRAG知识图谱双轨；设计组件库以JSON Schema形式抽象|
|**模型层**|按任务复杂度动态调度推理模型|深度模式核心Agent调用强推理CoT模型；简单/中等模式及格式化输出调用常规模型|
|**处理层**|核心PRD生成逻辑与Agent编排|LangGraph状态图引擎；支持逆向跳转、人工闸口、确定性校验器矩阵|
|**输出层**|生成并交付最终产物|Markdown PRD \+ 飞书同步 \+ JSON Schema原型 \+ Machine\-Readable Spec双轨输出|
|**交互层**|用户编辑与确认体验|非阻塞并发流式生成 \+ Git\-like Diff对比 \+ 按块独立编辑/重生成|

## 三、输入层与数据接入设计

### 3\.1 输入源并行可选架构

用户进入Web工作台后，可选择以下任意输入源**并行组合**使用，系统自动完成多源信息融合：

|输入源|标识|说明|
|---|---|---|
|文字需求/零散描述|A1|用户直接在输入框中描述需求，支持一句话简述或详细段落|
|飞书妙记会议链接|A2|粘贴飞书妙记URL，系统自动拉取逐字稿、总结和待办，二次抽象提取需求点|
|输入文件导入|A3|上传文件（实验记录、需求草稿、接口初稿、历史PRD等），系统自动分类管理|

### 3\.2 输入文件分类管理

输入文件（A3）按素材时效性分为"临时上下文"与"长期知识"两类，避免知识库污染和过期材料误引用：

|分类|包含内容|处理方式|生命周期|
|---|---|---|---|
|**临时上下文**|本轮实验记录、需求草稿、接口初稿等一次性素材|进入临时上下文区，仅在当前生成任务中注入Prompt|生成完成后由用户选择是否入库沉淀|
|**长期知识**|历史功能PRD、平台架构文档等可复用资产|进入知识库，进行切片、向量化和元数据标注|持久化存储，供后续检索复用|

**分类判定逻辑**：

1. **文件类型启发式判定**：根据文件名关键词（如"PRD"、"架构"、"模块设计"等）和文件内容结构特征初步分类。

2. **用户显式标注**：上传文件时提供"临时参考"与"长期入库"两个选项，由用户主动选择。

3. **AI辅助判定**：对未明确标注的文件，由大模型分析内容性质（如是否包含可复用的系统性架构描述），给出分类建议供用户确认。

### 3\.3 多源输入融合与冲突解决

系统在融合多源输入（文字、语音、历史文档）时，遵循明确的优先级规则与冲突检测机制，确保信息融合的准确性：

#### 3\.3\.1 信息优先级定义

在Agent 1（需求萃取与澄清智能体）的Prompt中显式设定信息权重：

```Plaintext
信息优先级（高 → 低）：
1. [当前手写文字需求] — 用户直接输入的需求描述，最高权威
2. [飞书妙记提取的核心结论] — 会议中产生的最新共识，次高权威
3. [历史PRD的默认业务逻辑] — 已有系统规则作为背景参考，最低权威
```

当低优先级来源的信息与高优先级来源产生矛盾时，以高优先级为准。

#### 3\.3\.2 冲突检测与提示面板

当AI在信息融合阶段发现不同来源间存在语义冲突时（如：历史PRD规定模型发布需算法负责人审批，但妙记中会议决策简化为自助发布），在中等/深度模式的阶段一自动弹出**冲突提示面板**：

- **冲突摘要**：简要描述冲突内容（如"历史PRD规定模型上线需Leader审批，妙记中决策为自助发布"）。

- **冲突来源标注**：标注每方信息的出处（文件名/妙记时间戳/手写输入）。

- **处理选项**：

    - 采用来源A（附理由预填）

    - 采用来源B（附理由预填）

    - 两者结合（用户自定义描述）

    - 暂时搁置，标记为待确认项

用户确认后，冲突解决结果将作为权威信息注入后续Agent工作流。

## 四、知识层与记忆检索设计

这是确保AI生成内容**不跑偏、有依据**的核心底座。知识层独立于输入层，为所有生成模式提供持久化上下文。

### 4\.1 历史PRD知识库（RAG检索增强生成）

- **数据来源**：用户通过输入层A3导入并标记为"长期知识"的历史PRD文档，以及系统使用过程中沉淀的PRD。

- **功能**：

    1. **实时检索**：生成新PRD时，将当前需求Embedding化，向量检索最相似的3\-5份历史PRD片段，作为"Few\-shot"示例注入上下文。

    2. **模板提取**：定时（如每月）扫描全部历史PRD，统计高频章节结构、常用语态和字段规范，自动生成/更新符合本项目组习惯的PRD模板。

- **技术选型**：Embedding模型（复用大模型Embedding能力）\+ 向量数据库（Chroma/Milvus）。

### 4\.2 平台架构快照

- **内容**：机器学习平台系统架构图、核心模块说明（数据预处理、特征工程、模型训练、模型服务、模型评估等）、技术栈清单、已有功能列表、数据库设计文档。

- **更新机制**：

    - *初期（手动）*：维护一份`project_context.md`文件，每次生成时自动注入System Prompt。

    - *中期（半自动）*：接入飞书Wiki或Confluence，通过定时任务拉取更新。

    - *后期（进阶）*：构建GraphRAG知识图谱，自动解析实体（模块/接口）间的依赖关系。

### 4\.3 GraphRAG知识图谱建设

GraphRAG知识图谱作为知识层的进阶能力，规划于Phase 2启动建设、Phase 3完成推理能力上线。其核心价值在于让系统具备跨模块连锁影响的推理能力——例如，当PRD涉及特征存储模块的改动时，系统可自动识别其对模型训练和数据校验两个下游模块的影响。

#### 4\.3\.1 知识图谱构建

系统利用大模型自动解析现有文档（历史PRD、平台架构文档、接口文档），提取实体和关系：

|要素|示例|
|---|---|
|**实体（Entity）**|FeatureStore模块、TrainingService接口、ModelRegistry模块|
|**关系（Relation）**|Depends on、Calls、Affects、Belongs to|
|**属性（Property）**|接口入参/出参Schema、模块负责人、业务线优先级|

构建"模块\-接口\-业务线"拓扑图，存储于图数据库（初期采用轻量级NetworkX，后期迁移至Neo4j）。

#### 4\.3\.2 图谱辅助推理

深度模式Agent 2（内部上下文分析智能体）在工作时，通过图谱检索直接注入上下文：

- **影响范围分析**：当PRD涉及修改某模块时，图谱自动追溯其依赖链路，注入提示如："⚠️ 注意：当前设计会影响\[特征存储\]和\[模型训练\]模块，涉及接口TrainingService\.submit和FeatureStore\.getFeatures"。

- **缺失依赖检测**：当PRD中提及某功能但未覆盖其依赖的底层模块时，主动提示补充。

- **历史变更追溯**：查询图谱中某模块的历史变更记录，辅助评估本次改动的风险等级。

### 4\.4 设计系统与组件库沉淀

- **用途**：为前端原型生成提供组件规范依据。

- **内容**：整理机器学习平台现有的前端UI组件（如训练监控图表、模型列表表格、实验对比卡片、参数配置表单等），以**JSON Schema**形式定义组件结构（详见第七章输出层设计）。

- **形式**：构建"组件字典"知识库，每个组件包含类型标识、属性Schema、嵌套规则、样式约束。通过连接Figma设计令牌（Design Tokens），确保渲染引擎输出的原型严格遵循平台现有视觉风格。

## 五、模型层与算力调度设计

### 5\.1 "推理\+协同"双模型架构

针对不同模式的Agent任务复杂度，采用大模型分流机制，平衡推理深度与响应成本。

|模型类型|选型建议|适用场景|核心优势|
|---|---|---|---|
|**强推理模型**|DeepSeek\-v4\-pro等具备长思考链（CoT）的模型|深度模式Agent 2（内部上下文分析）、Agent 3（功能规格定义）|通过深度逻辑推导，挖掘隐藏的非功能性需求和边界漏洞|
|**协同/常规模型**|DeepSeek\-V4\-flash|简单/中等模式对话、Agent 1（需求萃取）、Agent 4（格式化输出）|响应速度快、成本低，适配流式打字机输出|

### 5\.2 模型调度策略

```Plaintext
任务路由逻辑：
├── 简单模式 → 协同模型（Qwen-Long/DeepSeek-V4-flash）
├── 中等模式 → 协同模型（Qwen-Long/DeepSeek-V4-flash）
├── 深度模式
│   ├── Agent 1（需求萃取与澄清）→ 协同模型
│   ├── Agent 2（内部上下文分析）→ 强推理模型（DeepSeek-V4-pro）★
│   ├── Agent 3（功能规格定义）  → 强推理模型（DeepSeek-V4-pro）★
│   ├── Agent 4（PRD撰写与格式化）→ 协同模型
│   └── 校验器（确定性规则）     → 无需模型，规则引擎校验
```

### 5\.3 LLM适配层

**复用现有 `llm_client.py` + `LLMConfigProvider`**，无需重新开发。现有实现已支持：

- 多 Provider 预设（OpenAI / DeepSeek / 通义千问 / 硅基流动）
- 前端全局配置（API Key / Base URL / Model）
- SSE 流式响应
- 多模型切换

> **说明**：`backend/services/llm_client.py` 封装了 OpenAI 兼容接口调用，`frontend/src/components/LLMConfigProvider.tsx` 管理前端配置，已有 axios interceptor 自动注入请求头。后续新增模型路由逻辑（按模式分流）在此适配器上扩展即可。

## 六、处理层与Agent编排设计

### 6\.1 PRD生成三种模式

用户进入Web工作台后，首先根据需求复杂度选择模式。三种模式共享知识层能力，但处理深度不同。

|模式|适用场景|交互流程|调用模型|
|---|---|---|---|
|**简单模式**|需求明确、极速预览|输入一句话需求描述 → 调用大模型直接生成完整PRD（可选注入知识层参考）|协同模型|
|**中等模式**|需求方向明确但细节待定|系统引导3\-5轮结构化问答 → 信息完备度达阈值 → 模块化撰写PRD|协同模型|
|**深度模式**|复杂功能、零散资料多|智能体流水线 \+ 校验器矩阵 \+ 人工闸口 \+ 平台知识库/图谱注入|推理\+协同混合|

> 三种模式均可**独立使用**任一输入源，也可组合使用。系统会自动融合多源输入信息并解决冲突。

#### 6\.1\.1 中等模式详细设计（两阶段工作法）

- **阶段一：定型**：系统生成初始化工作空间，通过与用户对话完成**产品基础信息、JTBD分析、范围界定、页面流程**的确认。若检测到多源输入冲突，在此阶段弹出冲突提示面板。

- **阶段二：撰写**：采用**非阻塞并发流式生成**（详见第八章交互层设计），先展示大纲，用户可自由点击任一章节进入编辑或让AI重新生成，无需强制等待前置模块确认。

#### 6\.1\.2 深度模式详细设计（智能体流水线\+校验器\+人工闸口）

该模式针对"在线机器学习平台新功能开发"场景设计了4个专用智能体，去除了传统的竞品分析与外部用户研究环节：

|顺序|智能体角色|核心职责|输入来源|输出|调用模型|
|---|---|---|---|---|---|
|1|**需求萃取与澄清智能体**|将零散输入结构化，识别信息缺口并生成针对性追问；执行多源信息融合与冲突检测|用户输入的任一/组合素材（文字/妙记/文件）|结构化需求基础信息 \+ 补全信息 \+ 冲突清单|协同模型|
|2|**内部上下文分析智能体**|结合平台架构快照与GraphRAG图谱，分析功能在平台中的定位、模块依赖关系、影响范围与隐含需求|①的输出 \+ K2（平台架构快照）\+ K4（知识图谱）|平台上下文分析报告 \+ 影响范围预警|**强推理模型**|
|3|**功能规格定义智能体**|拆解功能点，编写用户故事，定义边界条件与验收标准|①\+②的输出|结构化功能规格书（JSON Schema）|**强推理模型**|
|4|**PRD撰写与格式化智能体**|按模板组装内容，润色语言，完成完整性校验，同步输出Machine\-Readable Spec|前三步所有输出 \+ 用户选定模板|最终PRD Markdown \+ spec\_schema\.json|协同模型|

### 6\.2 专用Agent编排引擎

#### 6\.2\.1 架构设计

处理层采用**LangGraph**或**MetaGPT**作为编排引擎，利用其原生"状态图（State Graph）"能力替代Celery硬编码状态机：

- **状态节点**：每个Agent、校验器、人工闸口均作为状态图中的一个节点。

- **边（Edge）与条件路由**：根据节点输出结果动态决定下一步走向（如校验失败→回退重试，校验通过→继续前进）。

- **状态持久化**：状态图的中间状态持久化至Redis，支持断点恢复和人工审核暂停/恢复。

#### 6\.2\.2 复杂流转支持

- **逆向跳转**：Agent 3（功能规格定义）发现信息不足时，自动回退至Agent 1（需求萃取）追问用户补充信息，而非以幻觉填补。

- **人工审核节点**：Agent 2（上下文分析）执行后，流程暂停在"人工审核节点"，等待平台架构师确认影响范围后继续流转。

- **Celery职责边界**：Celery仅承担最外层异步Job容器角色（如解析飞书妙记、打包原型文件、定时模板提取等独立耗时任务），不再承载Agent间复杂状态流转逻辑。

### 6\.3 深度模式校验器与人工闸口

深度模式在关键节点设置**确定性校验器**和**人工确认机制**，防止串行Agent流程中错误逐级放大。

#### 6\.3\.1 流转链路

```Plaintext
需求输入 → 萃取Agent → Schema校验 → 上下文检索 → 规格Agent → 边界/验收校验 → 人工确认 → 撰写Agent → 完整性/一致性校验 → 输出
                                                                                                    ↑
                                        (校验失败时回退至对应Agent重试) ──────────────────────────┘
```

#### 6\.3\.2 核心校验器矩阵

|校验器类型|触发位置|检查内容说明|失败处理|
|---|---|---|---|
|**Schema Validator**|萃取Agent之后|必填字段是否完整、格式是否合规|回退至萃取Agent追问补全|
|**Scope Validator**|规格Agent之后|是否出现超出当前需求范围的功能（范围蔓延检测）|标记超范围项，提示用户决定保留或删除|
|**Citation Validator**|规格Agent之后|生成内容是否有明确的知识库/输入依据（防幻觉）|标注无依据内容，提示用户核实|
|**Acceptance Validator**|规格Agent之后|每个功能点是否具备可测试的验收标准|回退至规格Agent补充验收标准|
|**Permission Validator**|规格Agent之后|是否遗漏角色、权限、数据范围控制|提示补充权限设计章节|
|**Risk Validator**|撰写Agent之后|是否缺失异常处理、兼容性、性能、审计等考量|标记缺失项，提示补充非功能需求|

#### 6\.3\.3 人工闸口设计

|闸口位置|触发条件|闸口内容|交互方式|
|---|---|---|---|
|**冲突确认闸口**|多源输入检测到语义冲突|展示冲突摘要 \+ 来源标注 \+ 处理选项|冲突提示面板（详见3\.3\.2）|
|**影响范围确认闸口**|Agent 2输出影响范围预警|展示受影响模块/接口/业务线清单|勾选确认 \+ 补充说明|
|**功能规格确认闸口**|Agent 3输出功能规格书 \+ 校验器通过|展示完整功能清单 \+ 用户故事 \+ 验收标准|逐项确认/修改/驳回重生成|

### 6\.4 信息完备度阈值（严格/快速）

系统预设两套PRD必备信息检查清单，用于在深度模式阶段一决定是否进入下一环节：

- **快速模式**：仅检查核心信息项（如：功能概述、主要用户角色、核心操作路径）。缺失项占比低于20%即可进入生成。

- **严格模式**：检查全部信息项（包括异常处理、性能指标、埋点要求等）。缺失项占比低于5%才允许进入生成，否则持续追问。

## 七、输出层与交付物设计

### 7\.1 交付物总览

|交付物|格式|用途|目标受众|
|---|---|---|---|
|结构化Markdown PRD|`.md`|人类可读的需求文档，标准PRD交付|产品经理/开发/测试|
|飞书云文档同步|飞书Docx|团队协作沉淀，在线评审|全员|
|高保真可交互原型|JSON Schema → 动态渲染|开发评审前的快速Demo|产品/设计/开发|
|Machine\-Readable Spec|`spec_schema.json` / `AGENTS.md`|AI编码助手直接读取，一键生成基础代码|AI编码助手（Cursor等）/开发|

### 7\.2 前端原型：JSON Schema驱动渲染

AI直接生成HTML存在标签未闭合、样式崩坏等风险。本系统采用JSON Schema驱动方案，实现低成本高保真的前端原型生成。

#### 7\.2\.1 设计方案

1. **组件库JSON Schema抽象**：在知识层将机器学习平台UI组件库（如Ant Design）抽象为JSON Schema规范。每个组件定义其类型、属性、嵌套规则。

```JSON
// 组件Schema示例 — 模型列表表格
{
  "component": "Table",
  "props": {
    "columns": [
      { "title": "模型名称", "dataIndex": "modelName", "key": "modelName" },
      { "title": "版本", "dataIndex": "version", "key": "version" },
      { "title": "状态", "dataIndex": "status", "key": "status" },
      { "title": "训练指标(AUC)", "dataIndex": "auc", "key": "auc" }
    ],
    "dataSource": [],
    "pagination": { "pageSize": 10 }
  },
  "children": []
}
```

2. **大模型输出规范化JSON**：大模型仅输出符合组件Schema规范的JSON数据，而非直接生成HTML代码。Token消耗显著降低（JSON比HTML token量减少约60%），同时保证输出结构的确定性。

3. **动态渲染引擎**：前端提供轻量级Render Engine，读取JSON数据并递归渲染为实际页面。引擎内置组件库映射表，将JSON中的`component`字段映射为实际React/Vue组件。

#### 7\.2\.2 优势分析

|维度|直接生成HTML|JSON Schema驱动|
|---|---|---|
|Token消耗|高（含大量标签和样式代码）|低（仅结构化数据）|
|样式一致性|难以保证（每次生成可能不同）|100%符合平台UI规范|
|标签错误率|高（未闭合/嵌套错误）|0（Schema校验保证）|
|可编辑性|低（改HTML成本高）|高（改JSON即可）|
|组件库更新|需重新训练/提示|更新Schema映射表即可|

### 7\.3 研发交付：输出Machine\-Readable Spec

传统Markdown PRD对AI编码助手（如Cursor）不够友好，容易产生理解偏差。本系统在输出Markdown PRD的同时同步输出结构化Spec文件，打通从PRD到代码的AI闭环。

#### 7\.3\.1 双轨输出策略

Agent 4在输出常规Markdown PRD的同时，同步输出一份符合AI编码器规范的`spec_schema.json`或`AGENTS.md`：

|输出格式|文件名|内容重点|消费方|
|---|---|---|---|
|人类可读|`PRD-{功能名}.md`|业务背景、用户故事、流程图、验收标准|人类团队成员|
|机器可读|`spec_schema.json`|接口入参限制、出参Schema、异常状态码定义、数据模型|AI编码助手|
|机器可读|`AGENTS.md`|项目上下文、编码规范指引、模块依赖说明、环境约束|AI编码助手|

#### 7\.3\.2 Spec Schema结构定义

```JSON
{
  "feature": "模型版本管理功能",
  "version": "1.0",
  "endpoints": [
    {
      "path": "/api/model/register",
      "method": "POST",
      "auth": { "required": true, "roles": ["algorithm_engineer", "admin"] },
      "request": {
        "body": {
          "modelName": { "type": "string", "required": true, "maxLength": 64 },
          "framework": { "type": "enum", "values": ["tensorflow", "pytorch", "xgboost"], "required": true },
          "artifactPath": { "type": "string", "required": true, "maxLength": 256 }
        }
      },
      "response": {
        "200": { "modelId": "string", "version": "string", "status": "string" },
        "400": { "error": "INVALID_ARTIFACT" },
        "403": { "error": "PERMISSION_DENIED" }
      },
      "validations": [
        "artifactPath必须为有效的模型文件路径",
        "同一modelName下版本号不可重复"
      ]
    }
  ],
  "dataModels": [
    {
      "name": "ModelVersion",
      "fields": [
        { "name": "modelId", "type": "string", "primaryKey": true },
        { "name": "modelName", "type": "string", "indexed": true },
        { "name": "version", "type": "string", "indexed": true },
        { "name": "framework", "type": "enum", "values": ["tensorflow", "pytorch", "xgboost"] },
        { "name": "status", "type": "enum", "values": ["registered", "staged", "production", "archived"] },
        { "name": "metrics", "type": "json", "description": "评估指标如AUC/F1/precision" }
      ]
    }
  ],
  "businessRules": [
    "同一模型仅允许一个版本处于production状态",
    "production状态的模型不可直接删除，需先归档"
  ]
}
```

#### 7\.3\.3 研发闭环

开发人员的AI编码助手（如Cursor）可直接读取Spec文件：

1. 解析`endpoints`自动生成前后端接口骨架代码。

2. 解析`dataModels`生成数据库Model定义。

3. 解析`businessRules`生成校验逻辑。

4. 解析`AGENTS.md`中的模块依赖说明，确保生成的代码放置在正确的目录结构下。

由此实现"AI写PRD"到"AI写代码"的完整闭环，缩短从需求到开发启动的周期。

### 7\.4 飞书云文档同步

- **场景**：生成的Markdown PRD直接沉淀至飞书团队空间，便于在线评审与协作。

- **实现要点**：

    - 调用飞书云文档API创建新文档。

    - 写入内容时使用**多行真实Markdown文本**（来源于文件或原生字符串），避免JSON字符串拼接导致的转义符问题。

    - 写入后回读校验，确保标题层级和表格格式无损。

### 7\.5 飞书妙记需求提取

- **场景**：需求在飞书语音会议中沟通完成，仅有录音或妙记链接。

- **输入方式**：用户在输入层A2中粘贴飞书妙记链接（可独立使用，也可与A1/A3组合）。

- **流程**：

    1. 用户粘贴飞书妙记链接。

    2. **复用现有代码**：通过 `feishu_client.py` 的 `get_minute_info()` 和 `get_transcript()` 方法（底层使用 `lark-cli` subprocess）获取逐字稿、会议总结和待办事项。

    3. 大模型对会议文本进行二次抽象，提取功能需求点、涉及的干系人和约束条件。

    4. 提取结果填入"需求萃取与澄清智能体"的初始输入，进入深度模式（也可供简单/中等模式使用）。

- **注意事项**：系统需申请飞书应用权限；飞书妙记转写存在月度额度限制，平台应做用量提示。

> **说明**：妙记解析功能复用现有 `meeting_todo_service.py` 的成熟实现。`lark-cli` subprocess 自动管理 token/keychain，无需额外配置飞书开放 API 凭据。

## 八、交互层与用户体验设计

### 8\.1 设计目标

提供灵活、直观的编辑与确认体验，支持局部修改不影响全局内容，消除串行等待。

### 8\.2 非阻塞并发流式生成

中等模式下采用非阻塞并发流式生成机制：

- **大纲先行**：系统快速展示PRD大纲结构（章节标题列表），用户预览整体框架。

- **按块独立生成**：用户点击任一章节，AI单独生成该章节内容，无需等待前置模块完成。

- **并发流式输出**：多个章节的生成可并发进行，每个章节独立流式打字机输出，互不阻塞。

- **随时介入**：用户在任一章节生成过程中均可暂停、编辑或重新生成，不影响其他章节。

### 8\.3 Git\-like Diff对比视图

当用户调整输入或触发局部重新生成时，界面呈现"修改前 vs 修改后"的代码级对比：

- **触发场景**：用户修改某章节的输入信息，或对某章节点击"重新生成"。

- **展示方式**：采用类似Git Diff的红绿对比视图，绿色标注新增内容，红色标注删除内容，修改行高亮。

- **逐项确认**：用户可逐条接受或拒绝AI的修改建议，而非全量覆盖。

- **版本快照**：每次生成或修改自动保存版本快照，支持回退至任意历史版本。

### 8\.4 冲突提示面板

多源输入冲突检测与提示面板的设计详见第3\.3\.2节。该面板在中等模式和深度模式的阶段一自动触发，展示冲突摘要、来源标注及处理选项，用户确认后结果注入后续Agent工作流。

### 8\.5 交互组件选型

|组件|选型|说明|
|---|---|---|
|Markdown 渲染|react-markdown + remark-gfm|复用现有组件，支持实时预览与分块编辑|
|对话流组件|自研|支持流式打字机效果、结构化问答卡片|
|Diff 对比组件|react-diff-viewer / monaco-diff|支持代码级 Diff 展示，Diff 由前端实时计算|
|模板配置面板|自研|章节模板的可视化配置与预览|
|多源输入选择器|自研|用户自由勾选输入源，并标注临时/长期|
|冲突提示面板|自研|冲突摘要 + 来源标注 + 处理选项|

> **说明**：MVP 阶段优先复用现有技术栈，Markdown 渲染使用 `react-markdown` 而非 Milkdown，减少额外依赖引入。

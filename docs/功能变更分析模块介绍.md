# 前端功能变更自动提取模块 — 介绍文档

> **目标读者：** 技术管理层  
> **分析仓库：** `algorithm-monorepo`（GitLab）  
> **编写日期：** 2026-07-06（V2.0 — 信号类型扩展至 14 类，AST 验证层，多仓库支持）

---

## 一、背景与解决的问题

### 痛点

团队每天有大量前端代码提交到 `algorithm-monorepo` 仓库，项目管理和 Code Review 时面临：

1. **变更分散**：一次迭代十几个 commit，散布在多个子应用和共享包中，人工梳理费时
2. **噪音干扰**：纯 UI 调整（样式、文案）与真正的功能变更混在一起，难以快速定位业务变化
3. **信息断层**：commit message 写法不统一，只看 Git log 无法了解完整的功能变更全貌
4. **跨服务联动**：ml-main（主应用壳）、ml-data（业务子应用）、_share（共享包）三者的变更相互影响，需统一视角

### 解决方案

**时间段指定 → 自动拉取代码 → AST 信号提取 → LLM 语义归纳 → 业务级变更报告**

用户只需选择时间范围，系统自动输出"新增了什么功能、修改了什么逻辑、下线了什么能力"，并区分出"纯 UI 调整"。

---

## 二、为什么主要分析 ml-data

仓库中三个前端子应用的角色和变更频率差异很大：

| 子应用 | 角色 | 变更频率 | 说明 |
|--------|------|---------|------|
| **ml-data** | 业务子应用（qiankun slave） | 🔴 高 | 资源管理、样本管理、模型训练、在线服务等核心业务页面，每天有大量功能迭代 |
| ml-main | 主应用壳（qiankun master） | 🟢 低 | 布局框架、菜单、鉴权、空间切换，半年内几乎无实质功能变更 |
| _share | 共享组件/工具包 | 🟡 中 | 通用组件和工具函数，变更少且多为被动的兼容性调整 |

**结论：ml-data 是功能变更的主要载体，ml-main 和 _share 作为辅助分析。** 默认配置为 `apps/algorithm/ml-data` + `apps/algorithm/ml-main` 双路径分析（2026-07-10 从单路径改为双路径，补齐 ml-main 的全局搜索等功能提取），用户可根据需要扩展至全部三层。

## 三、核心实现流程

```
用户选择时间段
      ↓
① 拉取远程仓库（裸仓库增量同步）
      ↓
② 定位 base/target commit（--before 时间点）
      ↓
③ 检出双版本代码到 worktree
      ↓
④ 生成 diff（name-status + numstat + raw patch）
      ↓
⑤ 项目知识快照（静态 AST 扫描，含路由/API/组件结构）
      ↓
⑥ AST 信号提取 + Import Graph 聚类（Node.js CLI）
      ↓
⑦ LLM 语义归纳（复用中控台 LLM 配置）
      ↓
输出：业务变更报告（新增/修改/下线/UI）
```

### 每个环节的作用

| 环节 | 耗时 | 方法 | 输出 |
|------|------|------|------|
| ① 拉取仓库 | 5-60s | `git clone --mirror` 或 `git fetch --all --prune` | 本地裸仓库 |
| ② 定位 commits | <1s | `git rev-list --before <时间> -n 1 refs/heads/master` | base/target 两个 commit hash |
| ③ 检出代码 | 5-10s | `git worktree add` 双版本并行检出 | 两个独立目录 |
| ④ 生成 diff | 2-5s | `git diff --histogram` + 噪音过滤 | 三份 diff 文件 |
| ⑤ 知识快照 | 5-15s | ts-morph 静态扫描（详见第四章） | JSON 项目结构描述文件 |
| ⑥ AST 分析 | 5-30s | 10 类信号提取 + Import Graph 聚类（详见第五章） | Feature Groups（结构化 JSON） |
| ⑦ LLM 归纳 | 10-30s | 快照 + 信号数据 → LLM 提取业务语义 | 变更报告 |

## 四、知识快照（Knowledge Snapshot）

### 是什么

知识快照是目标项目（Target 版本）的**静态项目结构描述文件**。它在 AST 分析之前生成，用于给 LLM 提供项目背景信息。

### 输入

| 输入 | 来源 | 说明 |
|------|------|------|
| Target 版本 worktree 路径 | Git 检出 | 项目最新代码的完整目录 |
| frontend_paths | 用户配置 | 要扫描的子应用路径列表（如 `apps/algorithm/ml-data`） |

### 输出（JSON 结构）

```json
{
  "projectName": "algorithm-monorepo",
  "generatedAt": "2026-07-03T10:00:00+08:00",
  "applications": [
    {
      "name": "ml-data",
      "path": "apps/algorithm/ml-data",
      "role": "qiankun slave",
      "routes": [
        { "path": "/dataApp/resourceManagement/list" },
        { "path": "/dataApp/sampleManagement/list" }
      ],
      "apiModules": [
        { "name": "resourceManagement", "endpoints": ["createResource", "listResources"] }
      ],
      "components": ["DynamicForm", "GlobalStateContainer"],
      "modules": ["resourceManagement", "sampleManagement", "modalTraining", "onlineService"]
    }
  ],
  "sharedPackages": [
    {
      "name": "@algorithm/basic",
      "path": "apps/algorithm/_share/components",
      "components": ["AppModal", "UserSelector", "FeiShuUserCard"],
      "exports": ["components/AppModal", "components/UserSelector"]
    }
  ]
}
```

### 实现方式

用 **ts-morph**（TypeScript AST 工具库）轻量模式加载项目代码，对每个 frontend_path 做以下操作：

1. **路由提取**：解析 `config/config.ts`、`config/routes.ts`、`.umirc.ts` 等配置文件，用正则匹配所有 `path:` 字段，按顺序提取路由表
2. **API 模块扫描**：扫描 `src/service/` 目录，收集每个子目录下的 API 端点文件
3. **组件目录扫描**：扫描 `src/components/` 目录，收集所有组件名
4. **页面模块扫描**：扫描 `src/pages/` 目录，收集所有页面子目录
5. **共享包扫描**：对 `_share` 路径，递归扫描所有子目录，收集组件和导出文件

**关键约束**：
- 零 LLM 调用，纯文件系统 + AST 正则扫描
- 不加载 `node_modules`，不解析 tsconfig 路径映射
- 禁用 TypeChecker，仅用词法分析级别的 AST 解析
- 5-15 秒完成，生成文件约 50KB

### 作用

1. **给 LLM 提供项目上下文**：LLM 本身不知道这个项目有哪些路由、API 模块、组件结构。有了快照，LLM 能理解"这个变更发生在哪个模块、影响哪些页面"
2. **辅助功能分类**：快照中的路由信息帮助 LLM 判断变更是否涉及用户可见的页面
3. **3 天自动过期**：快照存储为 JSON 文件，超过 3 天自动重新生成

## 五、AST 信号提取分析

### 是什么

AST 信号提取是变更分析的核心——将 Git diff 的原始文本**转换为结构化语义信号**，回答"变的是什么类型的代码"而不是"哪行变了"。

### 整体流程

```
原始 diff (raw.patch)
      ↓
① 解析 patch → HunkInfo[]（每个文件一个或多个 Hunk）
      ↓
② 对每个 Hunk 提取 14 类信号（正则 + AST 关键词匹配 + AST 验证层过滤）
      ↓
③ Import Graph 构建（分析 changed files 之间的 import 关系）
      ↓
④ 连通分量聚类（相互引用的文件归为一组 Feature Group）
      ↓
⑤ 决策树分类（给每个 Feature Group 打标签：新增/修改/UI）
      ↓
输出：Feature Groups（结构化 JSON）
```
91 groups → LLM 逐组提取 category + description
    → 按 type 分类（功能变更 / 功能下线 / UI）
    → 代码去重：名称前缀（前 8 字）+ 描述相似度匹配
    → 相同名称前缀的合并 evidence_files，取最长描述
    → 输出

### 输入

| 输入 | 来源 | 格式说明 |
|------|------|---------|
| raw.patch | `git diff --histogram` | 双版本完整 diff 文本 |
| 双版本 worktree 路径 | Git 检出 | 用于 Snippet 截取（取 before/after 代码片段） |
| frontend_paths | 用户配置 | 限定分析范围 |

### 第一步：Patch 解析（parsePatch.ts）

**输入**：`raw.patch` 文本

**实现**：
- 正则 `/^diff --git a\/(.+) b\/(.+)$/m` 匹配文件头
- 正则 `/^@@ -(\d+),(\d+) \+(\d+),(\d+) @@/` 匹配每个 Hunk 的起始行号和行数
- 按 `+` 行和 `-` 行分别提取 addedLines 和 removedLines
- 按 `new file mode` / `deleted file mode` 标记文件状态（A/M/D）
- 只保留在 `frontend_paths` 范围内的文件

**输出**：`HunkInfo[]`，每个 Hunk 包含：
```json
{
  "file": "apps/algorithm/ml-data/src/pages/training/BatchImport.tsx",
  "status": "A",
  "addedLines": ["export default function BatchImport() {", "  const [visible, setVisible] = useState(false)", "  return <Modal ...>"],
  "removedLines": [],
  "rawText": "@@ -0,0 +1,45 @@..."
}
```

### 第二步：14 类信号提取（9 个 extractor 文件 + astValidator.ts）

**实现方式**：对每个 Hunk 的 `addedLines` 做正则匹配 → 再通过 `astValidator.ts` 集中 AST 验证过滤假阳性，不依赖 TypeChecker

| 信号 | 优先级 | 提取器文件 | 正则匹配逻辑 |
|------|--------|-----------|-------------|
| NEW_ROUTE | P0 | `routes.ts` | `path:/path` 在 `config/config.ts` 中出现 |
| NEW_PAGE | P0 | `routes.ts` | `pages/` 目录下新增 `.tsx` 文件 |
| API_CALL | P1 | `api.ts` | `api.get/post`、`fetch()`、`axios.get`、`useRequest()` |
| STATE_ACTION | P1 | `state.ts` | `setXxx()`、`dispatch()`、`commit()`、`useState()` |
| PERMISSION | P1 | `permission.ts` | 关键词 `role`、`permission`、`auth`、`isAdmin` |
| HOOK_DEF | P1 | `hooks.ts` | `useXxx` 命名的函数声明 |
| EVENT_HANDLER | P2 | `event.ts` | JSX 属性 `onClick={}`、`onSubmit={}`、`onChange={}` |
| DATA_MODEL | P2 | `dataModel.ts` | `interface`、`type`、`enum` 关键字声明 |
| CONFIG_CHANGE | P2 | `config.ts` | 文件名匹配 `.env`、`vite.config`、`config/config.ts` |
| STYLE_ONLY | P3 | `style.ts` | 文件后缀 `.css/.scss/.less`，或非样式文件中无逻辑代码行 |
| GENERIC_CHANGE | P2 | 自动替换 | STYLE_ONLY 被验证器移除后替换为 GENERIC_CHANGE，归为 FEATURE_MODIFY |
| TEXT_CHANGE | P3 | `contentType.ts` | `constant.ts` 文件内容变更（字符串/对象字面量） |
| TYPE_CHANGE | P3 | `contentType.ts` | `types.ts` 文件新增 interface/type/enum |
| TEST_CHANGE | P4 | `contentType.ts` | `*.test.ts`/`*.spec.ts` 文件变更 |

**AST 验证层（astValidator.ts）**：

正则提取负责高召回率，AST 验证层负责高精确率。验证层接收正则发现的候选信号，用 ts-morph AST 节点逐一确认，策略为"保守兜底"：
- **确认假阳性** → 移除信号
- **STYLE_ONLY 被移除** → 替换为 GENERIC_CHANGE 信号，避免归入 UI 变更
- **不确定时** → 保留信号（宁愿漏假阳性，不错杀真信号） |

**STYLE_ONLY 的特殊处理**（`style.ts`）：
- 对非样式文件（`.tsx`/`.ts`），检查所有 addedLines 中是否有控制流语句（`if`、`for`、`return`、`switch`）、函数调用、事件处理
- 如果没有任何逻辑代码行，只有 JSX 属性赋值 → 判定为 STYLE_ONLY
- 样式纯净度验证：防止简单的样式修改被误判为功能变更

### 第三步：Import Graph 构建（importGraph.ts）

**输入**：`HunkInfo[]`

**实现**：
- 对每个 Hunk 的 addedLines 提取 `from '...'` 和 `import('...')` 语句中的模块路径
- 将每个文件视为一个节点，将 import 关系视为有向边
- 在 changed files 集合中查找匹配：`A.ts` 引用了 `B.ts` → 建立边 A→B
- 路径别名处理：`@/` 前缀映射为 `src/`

**输出**：`Map<file, Set<neighbor>>` 邻接表

### 第四步：连通分量聚类（cluster.ts）

**实现**：
- **Phase 1**：BFS 遍历 Import Graph，将有 import 关系的文件聚合成一个 cluster
- **Phase 2**：剩余孤立文件按目录层级聚类（同一目录下的文件归为一组）
- **Phase 3**：合并 page-logic/ ↔ pages/ 跨 cluster 对（同一功能的逻辑层和视图层合并）
- **Phase 4**：拆分 constant/types 文件为独立簇（3 文件以上的大簇，将 `constant.ts`/`types.ts` 拆出）

**输出**：`HunkInfo[][]`，每个子数组为一个 Feature Group

### 第五步：决策树分类（decisionTree.ts）

对每个 Feature Group，根据其包含的信号类型做优先级覆盖分类：

```
NEW_ROUTE / NEW_PAGE → NEW_FEATURE (P0)
API_CALL / STATE_ACTION / PERMISSION / HOOK_DEF → FEATURE_MODIFY (P1)
DATA_MODEL / CONFIG_CHANGE → INFRA_CHANGE (P2)
EVENT_HANDLER → UI_INTERACTION (P2)
STYLE_ONLY 或无信号 → STYLE_ONLY (P3)
```

### AST 分析的最终输出

```json
{
  "mode": "analyze",
  "summary": {
    "totalChangedFiles": 12,
    "analyzedFiles": 15,
    "featureGroups": 3
  },
  "featureGroups": [
    {
      "id": "fg_000",
      "type": "NEW_FEATURE",
      "priority": "P0",
      "confidence": 0.85,
      "nameHint": "NEW_PAGE",
      "files": [{ "path": "apps/algorithm/ml-data/src/pages/training/BatchImport.tsx", "status": "A", "signals": ["NEW_PAGE", "API_CALL"] }],
      "allSignals": ["NEW_PAGE", "API_CALL"],
      "snippets": [{ "file": "...", "before": null, "after": "export default function BatchImport()..." }]
    }
  ]
}
```

### 作用

1. **降维**：将原始 diff（可能数千行）压缩为结构化信号摘要（数十行），大幅减少 LLM 处理成本
2. **去噪音**：过滤空格、缩进、import 顺序修改、重命名等无关变更
3. **确定性**：所有信号提取和分类都是纯代码逻辑，结果可复现、不受 LLM 不稳定性影响
4. **聚类聚合**：通过 Import Graph 将分散在多个文件的变更合并为业务视角的 Feature Group
5. **客观置信度**：confidence 基于信号覆盖度计算，不是 LLM 自评

## 七、LLM 输入内容

### 14 类信号

传统的 diff 只能看到"哪行代码变了"，AST 分析能回答"变的是什么"：

| 信号 | 优先级 | 含义 | 示例匹配 |
|------|--------|------|---------|
| NEW_ROUTE | P0 | 新增路由 | `config/config.ts` 中发现新 `path:` |
| NEW_PAGE | P0 | 新增页面 | `pages/` 目录下新增 `.tsx` 文件 |
| API_CALL | P1 | API 调用变更 | `api.get/post`、`fetch()`、`useRequest()` |
| STATE_ACTION | P1 | 状态管理变更 | `setXxx()`、`dispatch()`、`commit()` |
| PERMISSION | P1 | 权限逻辑变更 | `role`、`permission`、`isAdmin` 关键词 |
| HOOK_DEF | P1 | 自定义 Hook | `useXxx` 命名的函数 |
| EVENT_HANDLER | P2 | 事件处理 | `onClick`、`onSubmit`、`onChange` |
| DATA_MODEL | P2 | 数据模型变更 | `interface`、`type`、`enum` 新增/修改 |
| CONFIG_CHANGE | P2 | 配置变更 | `.env`、`vite.config`、`config/config.ts` |
| GENERIC_CHANGE | P2 | 通用代码变更 | STYLE_ONLY 被移除后替换，归为 FEATURE_MODIFY |
| STYLE_ONLY | P3 | 纯样式变更 | CSS 文件或样式纯净度验证通过 |
| TEXT_CHANGE | P3 | 文案变更 | `constant.ts` 文件内容更新 |
| TYPE_CHANGE | P3 | 类型定义变更 | `types.ts` 新增 interface/type/enum |
| TEST_CHANGE | P4 | 测试变更 | `*.test.ts`/`*.spec.ts` 文件变更 |

### 变更聚类

信号提取后，通过 **Import Graph（导入关系图）** 的连通分量分析，将相互 import 的文件聚合成一个 Feature Group。例如：

- `BatchImport.tsx`（页面） + `api/training.ts`（API） + `hooks/useBatchImport.ts`（Hook） → 同一组"训练任务批量导入"
- 没有 import 关系的孤立文件 → 按目录层级聚类兜底

### 决策树

每个 Feature Group 根据其包含的信号类型，自动分类：

1. NEW_ROUTE / NEW_PAGE → **新增功能**（P0）
2. TEST_CHANGE → **测试变更**（P4）
3. TEXT_CHANGE → **文案变更**（P3）
4. TYPE_CHANGE → **类型定义变更**（P3）
5. API_CALL / STATE_ACTION / PERMISSION / HOOK_DEF → **功能修改**（P1）
6. DATA_MODEL / CONFIG_CHANGE → **基础设施变更**（P2）
7. EVENT_HANDLER → **UI 交互变更**（P2）
8. GENERIC_CHANGE → **功能修改**（P2）
9. 无信号 / 仅 STYLE_ONLY → **UI 变更**（P3）

LLM 按组逐一调用时，可以修正 AST 分类（仅允许 STYLE_ONLY ↔ FEATURE_MODIFY、UI_INTERACTION → FEATURE_MODIFY）。LLM 输出包含 `type` 字段，代码层最终覆盖：`"新增"`/`"新建"` 开头 → NEW_FEATURE，`"移除"`/`"删除"` 开头 → FEATURE_REMOVAL。

## 六、LLM 输入内容

### 输入给 LLM 的数据结构

```json
{
  "projectContext": {
    "name": "Algorithm Monorepo",
    "domain": "机器学习模型训练与管理平台",
    "apps": [
      { "name": "ml-main", "role": "qiankun master", "routes": [] },
      { "name": "ml-data", "role": "qiankun slave", "routes": [] }
    ]
  },
  "commit_messages": [
    "feat: add batch import for training tasks",
    "fix: adjust export permission for status=5"
  ],
  "feature_groups": [
    {
      "type": "NEW_FEATURE",
      "confidence": 0.92,
      "files": ["apps/algorithm/ml-data/src/pages/training/BatchImport.tsx"],
      "signals": ["NEW_PAGE", "API_CALL"],
      "snippet_before": "",
      "snippet_after": "export default function BatchImport() { ... }"
    }
  ]
}
```

三个组成部分：

| 部分 | 来源 | 作用 |
|------|------|------|
| `projectContext` | 知识快照（路由表、API 模块列表、组件目录） | 告诉 LLM 项目结构，帮助理解功能归属 |
| `commit_messages` | `git log --format=%s` | 提供开发者的原始描述，辅助 LLM 理解变更意图 |
| `feature_groups` | AST 信号分析结果 | 变更的精确代码级证据，包括信号类型、文件列表、Snippet |

### 关键设计：不传完整 diff 给 LLM

**改前（2026-07-10 前）**：传给 LLM 每个 group 的 `file_content`（第一个文件前 50 行），LLM 看不到实际 diff 行，只能靠文件路径和 signal 类型猜测变更内容，导致描述模糊、不稳定。

**改后（2026-07-10）**：传 `diff_snippets`（每个文件的 git diff patch，含前后各 50 行上下文），同时传 `signal_details`（含具体 API 路径、状态名、路由名等细节）。LLM 能看到完整的变更上下文，生成的描述更准确。

**diff 上下文行数**：`git diff --histogram -U50`（前后各 50 行），AST 工具截断到 5000 字符。

LLM 输入不是原始 diff 文本，而是经过 AST 信号提取和聚类后的**结构化摘要**。这样做的原因：

1. **Token 控制**：原始 diff 可达数万 token，信号摘要仅数百 token
2. **去噪音**：AST 层已过滤掉空格、缩进、import 顺序等无关变更
3. **聚焦业务**：信号类型（NEW_PAGE / API_CALL）直接告诉 LLM"这是什么类型的变更"
4. **确定性**：AST 分析是纯代码逻辑，不受 LLM 不稳定性的影响

### Confidence 不是 LLM 自评

每个 Feature Group 的 confidence 分数是**基于 AST 信号的客观计算**，不是 LLM 的自我评估：

- 基础分 0.5
- 同时有 NEW_ROUTE + API_CALL → +0.2
- 有 NEW_PAGE → +0.15
- 3 个以上文件参与 → +0.1
- 单文件单信号 → -0.2

## 八、LLM 调用策略（关键设计）

### 逐组调用而非批量归纳

**原始方案**：一次性将所有 Feature Groups 丢给 LLM，让 LLM 自行归纳分类。

**问题**：LLM 在批量归纳时极不稳定——相同输入三次输出分别为 59、27、92 项，`temperature=0` 和 `seed=42` 都不足以保证确定性。

**最终方案**：**逐组调用 LLM**，每组独立生成 `{category, description, type}`。AST 决策树决定初始分类，LLM 可以修正 type（仅限 STYLE_ONLY ↔ FEATURE_MODIFY），代码层做最终覆盖（"新增"开头 → NEW_FEATURE）。

### 单步调用（回归）

**原始方案**：两步调用（step1 概括 category + step2 展开 description）。

**问题**：两步报错率翻倍、失败组返回空 category 导致名称重复。

**最终方案**：回归单步调用，`max_tokens=8192`（2026-07-10 从 4096 提升），解析失败时重试 1 次，失败兜底用文件名作为 category。

### 结构化输出

每组输出格式：
```json
{
  "category": "训练任务批量导入",
  "description": "新增 BatchImport 页面，支持 Excel 批量导入训练任务，包含文件校验和错误提示。",
  "type": "NEW_FEATURE"
}
```

### 代码层覆盖规则

LLM 输出的 category 以这些关键词开头时，type 强制覆盖：
- `"新增"` / `"新建"` → NEW_FEATURE
- `"移除"` / `"删除"` → FEATURE_REMOVAL
- category 和 description 不能雷同
```

## 九、后处理流水线（提取 → 过滤 → 合并）

### 整体流程（2026-07-13 优化后）

```
AST 分析输出 N 个 Feature Groups
    ↓
① 逐组 LLM 调用 → {category, description, type, user_visible}
   （user_visible 在提取阶段由 LLM 同步判断，不合格的在此阶段直接丢弃）
    ↓
② 分类：按 type 分到 functional / removed / UI 三大类
    ↓
③ Level 1 目录聚类（_merge_similar_items）
    ↓
④ Level 2 堆内 LLM 合并（_llm_merge_batch）
    ↓
⑤ Level 3 全量二次合并（_llm_merge_batch）
    ↓
输出最终报告（仅含用户可见项）
```

### ① 逐组 LLM 提取 + user_visible 前置判断

**核心改动（2026-07-13）**：`user_visible` 判断从独立的后续阶段（`_filter_non_functional` + `_label_visibility`）前移到 per-group 提取阶段，LLM 在提取 `{category, description, type}` 时同时输出 `user_visible`，不合格的条目直接丢弃，不再进入后续合并。

**优势**：
- 减少后续合并的输入量（不可见项已过滤）
- 节省 2 次 LLM 调用（原 `_filter_non_functional` 分批 + `_label_visibility` 整批）
- 判断更准（结合 diff 上下文判断，而非事后看 description）

**user_visible 判断标准**：

→ user_visible = true（用户可见的功能变更）
- 新增/修改用户可交互的 UI 元素（页面、弹窗、按钮、列表、表单）
- 新增/修改用户可感知的业务逻辑（审批流程、发布策略、权限控制、搜索、对比）
- 新增/修改用户可触达的交互行为（点击跳转、筛选、排序、搜索、分享链接）

→ user_visible = false（用户不可见的技术调整）
- **埋点/追踪类**：新增埋点、重构埋点、修改埋点参数、添加追踪事件
- **基础设施/代理**：API 代理配置、路由配置、帮助路由、环境配置
- **纯代码调整**：调整枚举值顺序、修改常量定义、类型定义、接口定义
- **重构/重命名**：提取公共方法、重命名变量/函数、调整代码结构、拆分组件
- **工具函数**：纯数据转换逻辑、工具函数优化、数据映射调整
- **测试类**：新增测试用例、修改测试数据
- **属性/字段调整**：新增角色控制属性、修改字段属性、调整数据字段——数据结构层面字段增减，用户看不到字段本身
- **内部逻辑调整**：修改服务列表展开逻辑、调整匹配逻辑、修改去重逻辑——代码内部处理流程调整，除非直接改变用户界面或操作结果
- **内部状态管理**：修改面板展开标识、调整状态键值、改用内部 ID 作为标识——纯内部状态管理

**核心原则**："属性、字段、逻辑、状态、键名等内部调整，只要不直接改变用户看到的界面或操作结果，一律 false。"

### ② 分类（代码层）

LLM 返回的 `type` 字段结合 category 前缀，按以下优先级分到三类：

- **functional_changes**：NEW_FEATURE / FEATURE_MODIFY / INFRA_CHANGE / UI_INTERACTION / TEXT_CHANGE / TYPE_CHANGE（代码层 final 覆盖："新增"/"新建"开头 → NEW_FEATURE）
- **removed_features**：FEATURE_REMOVAL（"移除"/"删除"开头）
- **ui_updates**：STYLE_ONLY / UNKNOWN（纯 UI 变更列表）

### ③ Level 1 目录聚类

按 `pages/xxx` 模块名聚类，`page-logic/` 归一化为 `pages/`。同一模块（如 `pages/modalTraining`）的变更归到同一堆，不同模块的变更分开合并。

### ④ Level 2 堆内 LLM 合并（_llm_merge_batch）

每堆独立调用 LLM 进行语义去重合并。`max_tokens=8192`。

### ⑤ Level 3 全量二次合并

Level 2 堆内合并后直接对全部结果调用一次 LLM 合并，不再依赖证据文件匹配。处理跨批次的同类操作合并（如多个页面的埋点条目合并为一条）。

**合并 prompt 规则强化（2026-07-13）**：
- ✅ 必须合并：同一功能的不同部分（如实例对比 + 对比URL同步）、同一功能多入口
- ✅ 必须合并：同类操作的多个实例（散落在不同页面的埋点合并为"新增多处操作埋点"）
- ❌ 禁止合并：不同业务功能（如全局搜索 vs 实例对比）
- ❌ 禁止合并：不同功能即使涉及相似代码模式（都是埋点、都是新增字段）——只有当它们是同一功能的组成部分时才合并
- 拿不准是否同一功能时 → **不要合并**，保留为独立条目
- description **不要出现"合并"二字**

## 十一、使用方式

### 当前入口

AI 中控台 → 侧边栏"功能变更分析"

### 配置

1. **全局配置**（侧边栏底部）：LLM 配置 + Git 令牌
2. **页面配置**：仓库 URL、分支名、时间段、分析路径

### 典型场景

- **每日站会前**：选择"昨天"时间段，快速了解昨日功能变更
- **迭代回顾**：选择整个迭代周期，生成迭代变更报告
- **上线前审查**：选择从上次上线到现在的所有变更，确认变更范围
